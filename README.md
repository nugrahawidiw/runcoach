# runcoach

Run-coaching analysis fed by the **Strava API**: per-lap pace, grade-adjusted pace (GAP), aerobic
decoupling, cadence, efficiency, VDOT and CTL/ATL/TSB. It reproduces the analysis built in the
coaching session, but runs on your own machine.

## Quick start

1. **Register a Strava API app** at https://www.strava.com/settings/api
   - Authorization Callback Domain: `localhost`
   - Copy the Client ID and Client Secret.
2. `cp .env.example .env` and fill in `STRAVA_CLIENT_ID` and `STRAVA_CLIENT_SECRET`.
3. Optional: `cp profile.example.toml profile.toml` and set your bands, HR guide, resting and max HR.
4. Install and test (Python 3.11+):
   ```
   pip install -e ".[dev]"
   pytest
   ```
5. Authorize once (opens a browser, tokens are stored in `data/tokens.json`):
   ```
   runcoach auth
   ```
6. Pull recent runs, then analyze:
   ```
   runcoach sync --days 14
   runcoach analyze latest --kind easy      # easy | long | strides | intervals
   runcoach load --days 42 --source suffer  # or --source trimp
   runcoach vdot 26:17 5000
   ```

Start with `runcoach sync --days 7`: each new run costs 3 API calls (activity, laps, streams).

## What each command does

| Command | Result |
|---|---|
| `auth` | OAuth2 flow with the `read,activity:read_all` scope; refresh tokens are handled automatically |
| `sync` | Downloads runs into `data/cache/` once (activity, laps, full-resolution streams); stops cleanly on a rate limit and resumes next time |
| `analyze` | Lap table (pace, GAP, grade, HR, cadence), decoupling raw and grade-adjusted, efficiency, and flags (laps outside the Easy band, minutes above your HR guide) |
| `load` | CTL/ATL/TSB from Strava's `suffer_score` (Relative Effort) or from your own Banister TRIMP |
| `vdot` | VDOT plus equivalent 5K / 10K / half times |

## Things to know

- **Cadence:** Strava run cadence is one foot, so it is doubled to steps per minute. Glitch samples below 60 rpm are dropped.
- **Grade:** the REST laps do not carry grade, so it is averaged from the `grade_smooth` stream over each lap's index range.
- **Load numbers:** `suffer_score` may be missing on some accounts. TRIMP uses a different scale from Relative Effort, so CTL values will not match Strava-based numbers. Pick one source and stay with it.
- **Time bases:** Strava has moving, elapsed and best-effort-window times; races also have chip times. Label which one you use.
- **Rate limits:** read them from your API settings page; the client logs a warning at 80% of either limit.
- **Privacy:** `.env`, `data/` and tokens are git-ignored. Check Strava's current API Agreement for rules on how you may use and display the data.

## Garmin FIT files

Garmin gives you two kinds of FIT file, and `runcoach` reads both.

**1. Activity files (a run)**

- From Garmin Connect: open the activity, click the gear icon, **Export Original**. You get a `.zip`
  containing the `.fit`; you can pass the zip straight in.
- From the watch over USB: the `GARMIN/Activity` folder.

```
python -m runcoach fit-analyze "D:\Runs\run.fit" --kind long
python -m runcoach fit-import "D:\Runs\run.fit"       # store it in the cache
python -m runcoach analyze latest                         # now works on Garmin runs too
python -m runcoach load --source trimp                    # load from heart rate (no Strava needed)
```

Laps, per-second streams, grade (from altitude), GAP, decoupling and cadence use exactly the same code as the Strava path.

**2. Wellness files** (what your daily zips hold: `*_WELLNESS`, `*_SLEEP_DATA`, `*_HRV_STATUS` ...)

```
python -m runcoach wellness "D:\Garmin\2026-10-12.zip"
python -m runcoach wellness "D:\Garmin" --csv nights.csv    # a folder of zips: one row per night
```

Each night shows the sleep score and its parts, duration, HRV (last night, 7-day average, Garmin's balanced
range and status), the lowest heart rate in the sleep window, Garmin's resting HR, stress during sleep,
body battery change and an estimate of sleep stages.

## Weekly summary

```
python -m runcoach weekly                       # last 4 weeks
python -m runcoach weekly --weeks 9 --ctl0 17.13 --atl0 12.98
```

One row per Monday-to-Sunday week: runs, distance, moving time, average pace, longest run, and the
CTL/ATL/TSB line read at the week's end. Weeks with no runs still appear, so a rest week and its rising TSB
are visible. Load columns are blank for weeks before the cache starts rather than filled with a guess.
Planned vs actual is not included yet: the plan is not available as data (roadmap P1.7).

## Wellness trends

```
python -m runcoach trends "D:\Garmin"                      # a folder of nightly zips
python -m runcoach trends "D:\Garmin" --weak-nights 4
```

Per night: sleep score, HRV and its rolling mean, where HRV sits against Garmin's balanced range, status and
resting HR; then the resting-HR trend and how many weak nights have run consecutively. A night is weak when
the sleep score is below 60, HRV status reads Unbalanced, or HRV is below the balanced range. The streak
threshold that raises the alert is a parameter, not an agreed coaching rule.

## Charts

```
python -m runcoach analyze latest --kind long --chart long.svg
python -m runcoach fit-analyze "D:\run.fit" --chart run.svg
```

Pace per lap (left axis, faster upwards) and cadence (right axis, dashed), with the easy, goal and tempo
bands shaded behind. Inline SVG, so it needs no extra package and opens in any browser.

## Plan vs actual

```
python -m runcoach plan plan.toml                  # plan vs what the cache actually holds
python -m runcoach plan plan.toml --ics plan.ics   # all-day calendar events
python -m runcoach weekly --plan plan.toml         # planned runs and km per week, in brackets
```

Copy `plan.example.toml` to `plan.toml`. It is TOML (not YAML) because `tomllib` is in the standard library,
so the plan needs no extra package. Sessions are matched to runs **by date**: DONE if something was run that
day, MISSED if not, UNPLANNED for a run on a day with nothing planned. Distance short of plan is shown but
not judged. The `.ics` export needs the `icalendar` package: `pip install -e ".[ics]"`.

## Readiness

```
python -m runcoach readiness "D:\Garmin\2026-10-12.zip" --kind intervals
python -m runcoach readiness "D:\Garmin" --kind strides --legs-flat
```

Takes the latest night in the path and the planned session (`intervals`, `long`, `strides`, `gate`) and prints
the recommendation, the rule it came from, the inputs it used, and **the rule's status**: confirmed, in the
plan, suggested, or proposed and not confirmed. A proposal is never shown as an agreed rule. If the sleep score
or HRV status is missing it prints CANNOT DECIDE and names the missing input instead of guessing.

Things to know:

- HRV status follows the 7-day average against Garmin's balanced range, so a single night below the
  range can still read "balanced". The table prints the range so you can see both.
- "Low HR" is the median of the 5 lowest heart-rate samples in the sleep window; "Garmin RHR" is the
  value Garmin reports. They differ by design, so pick one for trends.
- **Sleep stages are an estimate.** The files do not say whether a stage timestamp marks the start or the
  end of the stage; the code assumes the end. Compare one night with Garmin Connect before trusting them.
- Two messages (sleep window and body battery) are read by their observed numbers, not from the public
  FIT profile. A firmware change could blank those columns; it will not produce wrong numbers silently.
- Times use the watch's own clock offset (from the file), so nights abroad follow the watch setting.

## What is tested

34 offline tests, built from real numbers in the coaching session (GAP, decoupling 4.02% / 6.92% / -1.33%, VDOT 36.1 / 33.7,
CTL steps, TRIMP), mocked API calls (token refresh, 401 retry, 429, pagination, sync resume), and a synthetic
Garmin run written as a real FIT file and read back. The wellness reader was also checked by hand against
eight real nights.
**The live Strava calls and the Garmin run-file reader have not been run on real data** by the author (no real run FIT was available). If something differs from the real responses,
start by inspecting `data/cache/*`.
